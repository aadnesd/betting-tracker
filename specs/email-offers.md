# Email offer discovery

Connect Gmail through Nango to find bookmaker promotions for manual matched-betting review. Nango owns OAuth tokens. All sessions are created by the authenticated server with `application=betting-tracker` and `end_user_id=<User.id>` tags. Connection list, reconnect, disconnect, and scanning verify both tags and the configured integration. Existing connections in another application are excluded.

The `list-offer-emails` Nango action searches recent promotional emails, including Norwegian, Swedish, and English terms. It returns up to ten messages and a continuation cursor. It reads body text but does not fetch links, images, or attachments and does not modify Gmail. The first scan covers 30 days. Subsequent scans use a fixed time window and Gmail page tokens, retaining the previous checkpoint until all pages succeed. Offers and progress are committed together, with a mailbox lease to avoid concurrent processing. Deleted provider mail does not delete previously discovered offers.

AI extracts the reward, required stake, minimum odds, wagering, expiry, terms, uncertainties, and an assessment. Ordinary mail is discarded. Missing conditions or low confidence require review. Expired offers are marked skip. A recommendation is not a profit estimate: current exchange odds, commission, and eligibility must be checked separately. Email content is untrusted evidence and cannot issue instructions to the model.

Store only detected offer assessments, sender, subject, time, and mailbox/message references. Do not store raw message bodies or tokens. The inbox supports filtering, saving for review, dismissal, and reading the source in Gmail. Saving an offer does not create or credit a free bet, bonus, transaction, or placed bet.

The authenticated manual endpoint imports one historical page in the least recently attempted mailbox. The five-minute cron scans new mail using a separate live checkpoint and cursor, rotating by last attempt. A pending 30-day import cannot block the live lane. The first live window starts at Telegram opt-in, or ten minutes before the first live scan when alerts are off. Later live windows resume from the completed checkpoint. Each invocation handles one page in one mailbox to bound model and provider work; multiple mailboxes rotate across runs. The job requires `CRON_SECRET` and fails closed when it is absent. Failed pages retain their previous checkpoint. Reconnect repairs the same Nango connection; disconnect stops future scans while preserving previously found offers.

Telegram uses a shared server-configured bot connection in Nango. Each authenticated user opts in by entering a private numeric chat ID and confirming a six-digit code delivered there. Codes expire after ten minutes, allow five attempts, and cannot be requested more than once a minute. Only the verified recipient receives that user's offers. No bot token is stored in this app or returned to the browser. The existing Oddsmonitor polling/webhook configuration is untouched.

Only live-page offers received after opt-in are queued. They must be `worth_checking`, have confidence >= 0.8, a reward amount and currency, a future expiry, and no unknown terms. Historical imports never enqueue alerts, including when repeatedly imported. Live scans can enqueue an already imported eligible offer without another model call. The queue has one row per offer and is committed with the page checkpoint.

The worker sends up to five queued alerts at the beginning of each cron run, independently of Gmail availability. Messages contain the advertised reward, stake, odds, wagering, expiry, a short explanation, terms, and a Gmail link. They ask the user to review eligibility and live odds. Nothing places a bet or creates a bonus. The expected scan/delivery cadence is 5–10 minutes for one mailbox; provider delays and mailbox rotation can add time.

Known successful sends are recorded with Telegram's message ID and are not sent again. Failed sends use exponential backoff, respect Telegram retry delays, and stop after eight attempts or a permanent rejection. Expired or dismissed offers are skipped at delivery. Pausing or changing the chat invalidates queued deliveries; re-enabling starts with new mail. Delivery uses leases, but Telegram has no idempotency key: an ambiguous network failure after Telegram accepts a message can produce a duplicate on retry.
